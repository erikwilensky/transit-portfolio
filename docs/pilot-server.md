# Pilot server

The demo began as a static app with everything saved in one browser. The pilot server makes it
real: one shared record on the server, live on every device, with real files, public share links
and sign-in.

## Layout

```
server/index.mjs        entry: loads every server/routes/*.mjs (sorted), serves dist/ and /api
server/lib.mjs          helpers: app.get/post/put/delete, send, readJson, readBody, cookies,
                        writeAtomic, middleware[], DATA_DIR, DIST, contentType,
                        clientIp(req), isHttps(req), onShutdown(fn)
server/store.mjs        the live record: `api` (src/api.js bundled for Node), `rev`,
                        `changed(info)` (bump, save, notify), `onChange(fn)`
server/build/api.js     generated by `npm run build:server` (part of `npm run build`)
server/routes/NN-*.mjs  one file per feature, `export default (app) => { ... }`
src/sync.js             browser side of the shared record
```

Run: `npm run build && npm run server` (port 8787, or PORT). In dev: `npm run server` plus
`npm run dev` (Vite proxies /api). Data lives in DATA_DIR (default `.data/`): `state.json`,
`uploads/`, `accounts.json`, `sessions.json`, `usage.json`, `feedback.json`, `audit.log`.

## Contracts between features

- **Routes**: `/api/state`, `/api/action`, `/api/undo`, `/api/stream`, `/api/reset` (shared record);
  `/api/upload`, `/api/files/:name` (files); `/api/public/*` (share links and verify, no sign-in);
  `/api/auth/*`, `/api/admin/*` (sign-in and accounts); `/api/me/export`, `/api/admin/students/:id/*`
  (PDPA copy and erasure); `/api/admin/usage` (pilot usage); `/api/feedback`, `/api/admin/feedback` (feedback); `/api/overview` (school overview); `/api/health`.
- **Sign-in guard**: the auth module pushes a function onto `middleware` that sets `req.user`
  (or null) on every /api request and refuses unsigned requests in pilot mode, except
  `/api/health`, `/api/public/*`, `/api/auth/*` and `GET /api/files/*`.
- **Mode**: `TP_MODE=demo` (default) keeps the persona switcher, tours and reset, no sign-in.
  `TP_MODE=pilot` requires sign-in and each person sees only their own role's screens.
  The browser reads the mode from `GET /api/auth/me` → `{ mode, user }`.
- **Presentations** (drafts, letters, custom pages, share links) are in the record:
  `store.drafts[studentId]`, read with `getDrafts()`, written with `setStudentDrafts(id, list)`.
- **No server** (plain static hosting, `vite preview`): the app falls back to saving in the
  browser, as before. Every feature must still work that way.

## The shared record (`server/routes/20-state.mjs`, `src/sync.js`)

- `GET /api/state` → `{ snapshot, rev }`; `GET /api/stream` (SSE) sends `{ rev }` on connect and after
  every `changed()`, plus a comment every 25s; `POST /api/reset` (demo mode only) → `{ rev, prev }`.
- `POST /api/action { fn, args, rec }` → `{ result, rev, prev }`. `fn` must be in `api.MUTATORS`
  (every function wrapped with `act()` at the bottom of api.js); in pilot mode `canAct(req.user, fn, args)`
  must agree (403 otherwise). Actions run one at a time.
- **Deterministic replay**: the browser runs a change first. Every id (`uid(prefix)`) and time (`nowIso()`)
  made during it is recorded in `rec`; the server's `api.runAction(fn, args, rec)` hands them back in
  order, so both copies end identical. Ids carry a per-page-load tag (`ev-12_k3f9q`), so two devices never
  make the same id; `isLiveId(id)` tells generated ids from seeded ones. Only the outermost call is sent.
  **New mutators**: use `uid()`/`nowIso()` (never `seq++`, `Date.now()` or `Math.random()` inside), keep
  arguments plain JSON, and add the function to the `act()` list.
- Server code that changes the record directly (admin, public views) calls `changed()`; every device
  hears it on the stream and fetches the new state.
- Browser: `main.jsx` calls `startSync()` after `loadAuth()` (demo, or signed in for pilot), never on
  `#/s` and `#/v` (`isPublicRoute()`). Changes queue and retry while the server is away (kept on the device for a pilot account: see "Offline capture"; header: "Offline,
  saving here"). Undo takes back one change on the server (see "Undo" below); only with no server does
  it put a whole snapshot back (`restore`).

## Undo (`server/history.mjs`, `POST /api/undo`)

Undo takes back one change (or the few a click made together) and keeps every change made since,
by anyone. The server keeps each change as the steps that made it (`{ fn, args, rec }`, who, when),
in segments that each start from a saved copy (a checkpoint every 20 changes), about the last 200
changes and at most 2 hours (`UNDO_MAX`, `UNDO_WINDOW_MS`). On disk: `DATA_DIR/history/cp-<rev>.json`
and `log.jsonl`; if they do not end at the record's revision on start, history starts again.

- `POST /api/undo { rev }` or `{ revs: [..] }` → `{ rev, prev, undone: [revs], skipped: [{ rev, fn, error }] }`.
  The server goes back to the checkpoint before the change and replays every later change except the
  undone ones, with their recorded ids and times (`api.runAction`, nothing re-recorded). A later change
  that now fails (it needed what was undone) is left out and listed in `skipped`. Then `changed()`, so
  every device fetches the result. The undo is itself an entry in the history.
- Refusals (plain words in `error`): 403 not your change (pilot; admins may undo anyone's, demo: anyone),
  409 already undone or already left out, 410 too old or no longer in the history, 400 an undo itself.
- A change the history cannot replay starts it again, so nothing before it can be undone: a reset, a
  whole-record `restore`, an action that failed, or server code that changed the record without an
  api.js change (`api.notify` from a public page). Server code calling api.js changes directly (adding
  a student, a public page view) is caught by the server's action hook and stays replayable.
- Browser: `api.markOf(snapshot)` is the change count when a snapshot was taken; the toast keeps it and
  `undoSince(mark, upto)` in `src/sync.js` waits for those changes' server revs (queued changes go first),
  then queues the undo. The screens keep calling `toast(msg, snapshot())` as before. With no server,
  Undo restores the snapshot as before. Tests: `server/test/undo.test.mjs`, `scripts/checks/sync.cjs`
  (two devices), `auth.cjs` (pilot rules), `undo.cjs` (no server).

## What the server does for every request

- **Security headers** on every response: `X-Content-Type-Options: nosniff`,
  `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: SAMEORIGIN`, a
  Content-Security-Policy, and `Strict-Transport-Security` when the visitor came over HTTPS. The
  policy allows the app's own files, Switzer from Fontshare and the theme fonts from Google Fonts,
  pictures from `https:`, `data:` and `blob:`, and inline scripts (needed by a student's own site
  in the Code tier, which runs in a sandboxed `srcdoc` frame that inherits the policy). It allows no
  other script hosts and no `eval`. A feature that needs another host (an embed, an outside API)
  adds it to `CSP` in `server/lib.mjs`; `TP_CSP` replaces the policy without a code change.
- **Compression**: html, js, css, json, svg and txt files from `dist/` are sent brotli or gzip
  compressed (made once, kept in memory), with an ETag so a reload costs a 304. `send()` also
  compresses JSON replies of 1 KB or more. Event streams are not touched.
- **Request log**: one line per `/api` request, to stdout (`docker compose logs`):
  `2026-10-27T21:50:57.123Z 203.0.113.9 GET /api/state 200 4.2ms u=<user>`. No bodies, no query
  strings. `LOG_REQUESTS=0` turns it off.
- **Graceful shutdown**: on SIGTERM (`docker stop`, a redeploy) or Ctrl+C the server stops taking
  connections, ends open event streams (browsers reconnect to the new server), lets requests in
  flight finish (up to `SHUTDOWN_TIMEOUT_MS`, 8 s), runs the `onShutdown` hooks, and exits. Saves
  are written straight to disk, so nothing waits in memory; a module that does keep something in
  memory registers a flush with `onShutdown(async () => ...)`.
- **Start check**: if `DATA_DIR` cannot be written, the server stops at once with a clear message.

### Behind cloudflared: `clientIp(req)` and `isHttps(req)`

The visitor reaches the Mac through Cloudflare, so the server's peer is cloudflared (through
Docker's gateway), not the visitor. Use these helpers from `server/lib.mjs` instead of
`req.socket.remoteAddress` or guessing the scheme:

- `clientIp(req)`: the visitor's IP address. From a trusted peer it takes `CF-Connecting-IP`, else
  the last `X-Forwarded-For` entry (the one the nearest proxy added; earlier ones can be forged).
  Use it for rate limits, sign-in attempts and the audit log.
- `isHttps(req)`: true when the visitor used HTTPS (a TLS socket, or a trusted proxy's
  `X-Forwarded-Proto: https` or `CF-Visitor`). Use it to add `Secure` to cookies.

Who is trusted is `TRUST_PROXY`: `auto` (default) believes loopback and private addresses, which
is cloudflared on the Mac or Docker's gateway; `all` believes anyone; `none` never. The compose
file publishes the ports on 127.0.0.1 only, so nothing but the Mac itself (cloudflared) can reach
the server and forge those headers.

## Deploy on the Mac (Docker)

Everything runs in Docker; the Mac needs no Node. The folders:

```
/Users/erik/Server/transit-portfolio            the repo (git pull here)
/Users/erik/Server/transit-portfolio-data       the demo's data   (TP_DATA)
/Users/erik/Server/transit-pilot-data           the pilot's data  (TP_PILOT_DATA, only with the pilot)
/Users/erik/Server/transit-portfolio-backups    backups and backup.log
```

**Every update** is one command, safe to run as often as you like:

```sh
cd /Users/erik/Server/transit-portfolio
scripts/deploy-mac.sh
```

It pulls the code (`--no-pull` to skip), creates `.env` from `.env.example` the first time, builds
the image while the old server keeps running, swaps containers, waits for `/api/health`, and prints
the status. If the new server does not come up it shows the last log lines and the command to put
the old static site back.

**Settings** are in `.env` (not committed; every line also reaches the server):

- `TP_MODE=demo` (persona switcher, tours, reset) or `TP_MODE=pilot` (sign-in).
- `TP_START=empty` (default for `transit-pilot`; pilot mode only): a data folder with no `state.json`
  yet begins with the school's lines and no fictional people. Anything else starts from the demo's
  seeded record. It never touches a record that already exists. See "Class lists and a clean start".
- `COMPOSE_PROFILES=pilot` also runs a real pilot, `transit-pilot`, on port 8081 with
  `TP_MODE=pilot` and its own data folder, next to the demo on 8080. Its own settings can go in
  `.env.pilot`. To publish it, add a second hostname in the Cloudflare tunnel pointing to
  `http://localhost:8081`.
- `TP_BIND=0.0.0.0` opens the ports to the local network (default: this Mac only).
- `SMTP_URL` and `MAIL_FROM` (optional) email setup and forgot-password links; `AUTH_IP_LIMIT` (default
  300) is how many failed sign-ins one address may make in 15 minutes. See "Sign-in help" below.

Handy commands, from the repo folder: `docker compose ps` (status), `docker compose logs -f`
(live log), `docker compose restart`, `docker compose down` (stop; the data stays).

### Switching over from the nginx container (once)

Today an `nginx:alpine` container called `transit-portfolio` serves `dist/` on port 8080. The
deploy script replaces it: it removes a container of that name only when it is an nginx image that
compose did not create, then starts the Node server on the same port, so the tunnel needs no
change. The first run takes a few minutes (it downloads Node and builds); the site is down only for
the few seconds between the two containers.

```sh
cd /Users/erik/Server/transit-portfolio
git pull
chmod +x scripts/*.sh             # only if git did not keep them executable
scripts/deploy-mac.sh --no-pull
curl -sI https://transit.wilenskycs.online | grep -i content-security   # through the tunnel
```

The demo starts from the seeded record; from then on it lives in `transit-portfolio-data`.
The old `docker run ... node:22-alpine ... npm run build` step is no longer needed.

To go back to the static site: `docker compose down`, then the old
`docker run -d --name transit-portfolio --restart unless-stopped -p 8080:80 -v "$PWD/dist":/usr/share/nginx/html:ro nginx:alpine`.

### Keeping the Mac awake

The tunnel drops when the Mac sleeps. Docker Desktop must also start at login (Settings, General,
"Start Docker Desktop when you sign in"); containers come back by themselves (`restart:
unless-stopped`). For the Mac:

- Plugged in: System Settings, Battery (or Energy), Options: turn on "Prevent automatic sleeping
  on power adapter when the display is off", or `sudo pmset -c sleep 0`.
- On battery: `caffeinate -i` keeps it awake while it runs, for instance in a Terminal tab for an
  event; `sudo pmset -b sleep 0` stops battery sleep altogether (costs battery). Closing the lid
  still sleeps a MacBook unless it has power and an external display.
- Run cloudflared as a service (`sudo cloudflared service install <token>`) so the tunnel
  reconnects by itself after a sleep.

## Backups

`scripts/backup.sh` packs each data folder into
`../transit-portfolio-backups/<folder>-YYYYMMDD-HHMMSS.tar.gz` and keeps the newest 30 of each
(`KEEP=60 scripts/backup.sh` to keep more, `BACKUP_DIR=/Volumes/Backup/transit` to put them
elsewhere). It is safe to run while the server is up: the record is always saved by writing a new
file and renaming it, so a backup never holds half a save.

Nightly at 02:30 with launchd (if the Mac sleeps through it, launchd runs it on waking):

```sh
mkdir -p /Users/erik/Server/transit-portfolio-backups
cp docs/launchd/online.wilenskycs.transit-backup.plist ~/Library/LaunchAgents/
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/online.wilenskycs.transit-backup.plist
launchctl kickstart gui/$(id -u)/online.wilenskycs.transit-backup     # run it once now
tail /Users/erik/Server/transit-portfolio-backups/backup.log
```

Backups on the same disk do not survive the disk. Copy the backups folder somewhere else from time
to time (Time Machine covers it if `~/Server` is included).

## Restore

1. Pick a backup: `ls -1 ../transit-portfolio-backups/`.
2. Stop the server and keep the current data aside (nothing is deleted):

   ```sh
   cd /Users/erik/Server/transit-portfolio
   docker compose stop transit-portfolio
   mv ../transit-portfolio-data ../transit-portfolio-data.before-restore-$(date +%Y%m%d-%H%M%S)
   ```

3. Unpack the backup next to the repo (it recreates `transit-portfolio-data`) and start again:

   ```sh
   tar -xzf ../transit-portfolio-backups/transit-portfolio-data-20261027-023000.tar.gz -C ..
   docker compose up -d
   curl -s http://127.0.0.1:8080/api/health
   ```

For the pilot it is the same with `transit-pilot` and `transit-pilot-data`. To start the demo
from the seeded record instead, stop it, move `transit-portfolio-data` aside, and start it: the
server makes an empty folder and begins again from the seed.
## Sign-in and accounts (`server/auth.mjs`, `server/routes/10-auth.mjs`)

- **Accounts** in `DATA_DIR/accounts.json`: `{ id, email, name, kind, studentId | teacherId | children,
  admin, password: { salt, hash }, setup?, createdAt }`. `kind` is a persona kind (`student`, `advisor`,
  `teacher`, `counsellor`, `coordinator`, `leadership`, `parent`) or `admin` (no record). Leadership can
  be flagged `admin`. Passwords: `crypto.scrypt` with a per-user salt, compared in constant time.
- **Sessions**: a random token in the `tp_session` cookie (HttpOnly, SameSite=Lax, Secure over https or
  with `COOKIE_SECURE=1`); only its SHA-256 is stored, in `DATA_DIR/sessions.json`, for 30 days.
  Non-GET requests with a cross-site `Origin` are refused (except `/api/public/*`).
- **First run**: with no accounts, the server prints a one-time admin setup link (`/#/setup/<token>`,
  valid until restart). There is no default password. Set `PUBLIC_URL` to print the real address.
- **Routes**: `GET /api/auth/me` → `{ mode, user }` (user carries its linked `record`);
  `POST /api/auth/login { email, password }` (see "Sign-in help" below for the limits); `POST /api/auth/logout`;
  `POST /api/auth/password { current, password }` (signs out other devices);
  `GET /api/auth/setup/:token`, `POST /api/auth/setup { token, password, name?, email? }` (ends every
  other session of that account).
  Admin only: `GET /api/admin/accounts` (accounts, students, teachers), `POST /api/admin/accounts`
  (create; link with `studentId`/`teacherId`/`children`, or `newStudent: { name, year, programme }` /
  `newTeacher: { name, role }`; returns a one-time `setupUrl`, valid 7 days, and `emailed`), `POST /api/admin/accounts/:id`
  (edit role or link), `POST /api/admin/accounts/:id/reset` (new setup link, `{ setupUrl, emailed }`; ends the
  old password and sessions), `POST /api/admin/accounts/:id/dismiss` (clears a forgot-password request),
  `DELETE /api/admin/accounts/:id` (the record stays).
- **Guard**: sets `req.user` (the account, or null) on every /api request. In pilot mode it answers 401
  for unsigned requests outside the open routes, and 403 for `/api/reset` unless the user is an admin.
- **New records**: `api.addStudent({ name, year, programme })` (British Year 7–13; `grade = year - 1`,
  `onboarding: true`, empty map) and `api.addTeacher({ name, role })`. Teachers now live in the record
  (`store.teachers`). Both are idempotent when given an existing `id`.
- **`canAct(user, fn, args)`** (exported from `server/auth.mjs`, re-exported by `10-auth.mjs`): call it in
  `/api/action` before running a mutator and answer 403 when false. Admins: anything but `restore`.
  Whole-school staff (leadership, coordinator, counsellor): any mutator except `resetDemo`, `restore`,
  `addStudent`, `addTeacher`, `importRoster`, `eraseStudent`. Advisors and teachers: see "Who sees which students" below. Students: only
  the mutators in `STUDENT_FNS`, and only when every student the call touches (`touchedBy`, looked up from
  the station, inbox item, request or evidence request) is their own `studentId`, never as a teacher.
  Parents: `answerConsent` for their own children, and `setFamily`. Everyone signed in: `recordView`,
  and `markNotificationsRead` for their own keys only (see Notifications). `setLang` (the demo's one shared
  language) is admin only in a pilot: each person's language is on their account (see "Thai for families").
- **Browser** (`src/auth.js`): reads the mode from `/api/auth/me` (no server, or demo → demo). In pilot it
  builds the signed-in person's persona in the PERSONAS shape (`personaFor`) and installs it with
  `setPilotPersona`, so `personaById` always returns it. `navOf(p)` gives a persona's navigation
  (an admin gets Accounts). `src/main.jsx` shows `screens/SignIn.jsx` when signed out, except on the
  public `#/s`, `#/v`, `#/p` routes and `#/setup/<token>`.

### Sign-in help: limits, forgot password, sessions, email

- **Failed sign-ins** are counted per email and per visitor address, where the address is lib's
  `clientIp(req)` (`CF-Connecting-IP` behind cloudflared), never the Docker gateway. Per email: slowed
  after 3, refused for 15 minutes after 10. Per address: a whole school shares one public address on
  its Wi-Fi, so the limit is loose: refused after `AUTH_IP_LIMIT` (default 300) in 15 minutes, slowed
  only after 150. The refusal says "Too many tries. Wait 15 minutes or ask your teacher." Any new
  setup link for that account lifts the per-email block.
- **Forgot password**: `POST /api/auth/forgot { email }` → always `200 { ok: true, emailed }`, whatever
  the email (`emailed` says only whether this server has mail set up). The work happens after the
  reply. At most 3 per email (the rest are ignored, same answer) and 100 per address (429) per
  15 minutes. Without mail it sets `account.resetRequest = { at, n }`; the admin sees these at the top
  of Accounts ("Make a new sign-in link" calls `/reset`, which clears it; "Dismiss" calls `/dismiss`).
  A new password from any setup link also clears it.
- **Advisors** (any staff account whose `teacherId` is the student's `advisorId`, and admins):
  `GET /api/advisor/students/:studentId/account` → `{ account: { id, name, email, hasPassword,
  resetRequest } | null }`, `POST /api/advisor/students/:studentId/reset` → `{ account, setupUrl, emailed }`.
  Student accounts only, so an advisor can never reset staff, family or admin accounts. Shown as
  "Sign-in help" on the advisor's student page (pilot only).
- **Sessions**: `GET /api/auth/sessions` → `{ devices }`; `POST /api/auth/logout-everywhere` ends every
  session of the signed-in account, this one too. The account menu shows "Signed in on N devices" and,
  with more than one, "Sign out everywhere". Changing the password ends the other sessions.
- **Email (optional)**: set `SMTP_URL` (`smtp://user:pass@host:587`, STARTTLS, required before sending
  the password except to localhost; or `smtps://…:465`; URL-encode `@` in the user as `%40`) and
  `MAIL_FROM` (`Transit Portfolio <noreply@school>`). Then new accounts and new links are also emailed
  (the admin still sees the link, in case the email does not arrive), and "forgot password" emails a
  link straight away; that link leaves the old password working until it is used, so nobody can lock
  someone out by asking. If the email fails, the request goes to the admin as above. `server/mail.mjs`
  is a minimal SMTP client (AUTH PLAIN or LOGIN); it never logs the password, the message or the link.
  Without these settings nothing is emailed: admins and advisors hand out links themselves.

### Not enforced yet

- `canAct` checks who owns the target and, for advisors and teachers, which teacher a call acts as; not
  every field of the arguments (a whole-school role can still act as any teacher, `addGoal(.., by)` etc.).
  `restore` (a whole earlier copy) is refused for everyone in a pilot, since each browser holds only part
  of the record; Undo goes through `/api/undo`, which rebuilds on the server's whole record.
- In the browser the record is still also saved in localStorage; signing out clears it.
- **Public pages** (`server/routes/40-public.mjs`, `src/publicRoute.js`, `src/screens/PublicPage.jsx`):
  `#/s/<token>` and `#/v/<code>` never load or sync the full record (`isPublicRoute()`). With a server,
  `GET /api/public/share/:token` returns a pruned `{ store, seq, evSeq }` (one student, the stations that
  presentation shows, public reflections, this one link), loaded with `loadPublic()` and never saved;
  404 unknown, 410 revoked or expired. Gated links send no stations until `POST …/open { email }`.
  `POST …/extend` and `…/ask` carry the reader's requests. `GET /api/public/verify/:code` returns one
  station's verification record. Share URLs are absolute; set `VITE_PUBLIC_URL` at build time when the
  app is built or opened somewhere other than its public address. Tests: `npm run test:server`,
  `BASE=http://localhost:8787 node scripts/checks/public.cjs`.

## Notifications (`src/api.js`)

- **Recipient keys**: `toStudent(sid)`, `toTeacher(tid)`, `toFamily(sid)` give the demo persona id when the record
  has one (`maya`, `nair`, `parent`…) and otherwise `st:<studentId>`, `t:<teacherId>`, `fam:<studentId>` (that
  child's family). `toRole(kind)` is `role:<kind>`, for whoever holds a role (a new sub-line goes to
  `role:coordinator`). Every `notify(to, text, go)` uses them, and `go.persona` is the same key.
- **A person's bell**: `notifyKeys(personaOrAccount)` lists every key a person reads: their persona id (not `me`),
  `st:` and `toStudent` for a student, `t:`, `toTeacher` and `role:<kind>` for staff, `fam:` and `toFamily` for
  each child of a parent. `getNotifications(keys)` and `markNotificationsRead(keys)` take one key or a list. A
  seeded record answers to both its demo id and its `st:`/`t:` key. In pilot mode `canAct` lets a person mark
  read only their own keys.
- **Who acted**: texts name the person who acted. `decideBranch(id, ok, mergeInto, by)` and
  `nudgeMilestone(studentId, milestone, by)` take the coordinator's teacher id (left out: the demo's Ms Brandt);
  `CommentDialog` passes the counsellor's. `shortName('Ms Clara Brandt')` is `Ms Brandt`. Demo texts are unchanged.
- A family's answer to a consent request goes to the student's advisor (`toTeacher(advisorId)`); in the demo
  Mr Whitfield still hears about every seeded student.
- A pilot parent linked to a seeded child that has a demo family (`st-06`, `st-09`) also reads the demo parent's bell.
- Tests: `server/test/notifications.test.mjs`, `node scripts/checks/notifications.cjs` (its own pilot server: a new
  student asks a new teacher, the teacher endorses, both bells update live).
## Who sees which students (`server/scope.mjs`, pilot only)

Each signed-in person downloads only their own part of the record, and advisors and teachers change
only the students they work with. Demo mode still sends the whole record to everyone.

- **`reachOf(user)`** → `null` (the whole school: admin, leadership, coordinator, counsellor) or a `Set` of
  studentIds. A student: themselves. A parent: their children. An advisor or teacher (`teacherReach`):
  students they advise (`advisorId`), students enrolled in classes they teach (`classes[].teacherIds`,
  `enrolments[]`, from the roster import; missing is `[]`), students who sent them an endorsement or
  evidence request, whose goals they sponsor, whose stations they endorsed, whom they sent a prompt,
  whose comments they wrote or were asked about (`by`, `to`, `teacherId`, `asked[]`), who are on their
  class tasks or carry their class endorsement in an inbox, and whose DP work they supervise.
- **`scopedSnapshot(user)`** → `{ store, seq }` in the shape `api.snapshot()` uses; `GET /api/state` sends it
  in pilot mode. Students outside reach are gone entirely (records, stations, reflections, endorsements,
  tags, drafts, inbox, requests, prompts, comments, activity, consent, CAS, DP, link views…). For the
  students in reach it keeps what that person may read, by `VISIBLE_TO` (now exported from api.js), as
  `getStudentMap(viewer)` applies it: a student's own record in full; a child as the family view shows it

## A student's data: a copy and erasure (`server/routes/50-pdpa.mjs`, `server/zip.mjs`)

Thailand's PDPA gives a student (and their parent) the right to a copy of their data and to have it removed.

- **What counts as theirs** is decided in `src/api.js` by `studentData(id, alsoTo)` (read) and the mutator
  `eraseStudent(id, alsoTo)`, which share one rule, generic so new collections are covered: a list item is
  theirs when one of its own values (or one inside a plain object on it) is their id, one of their stations,
  presentations, share links or other items, or it is addressed `to` their persona or account ids (`alsoTo`);
  a keyed entry is theirs by its key (`drafts[id]`, `tags[stationId]`, `linkViews[token]`, `answered['st-01:…']`).
  A notification to someone else that names them or quotes one of their station titles is theirs too.
  Other people's items that list their id (a class task's `submitted`) keep the item and lose only the id.
- **Copy**: `GET /api/admin/students/:id/export` (admin) and `GET /api/me/export[?student=id]` (a student:
  their own, whatever is asked; a parent: one of their `children`, the first by default; an admin: anyone;
  staff: 403). Answers a ZIP (stored, no compression; `zlib.crc32`, with a fallback for older Node):
  `README.txt` explaining each file, `student.json`, `activity.json` (the full log `getActivity` shows),
  one `<collection>.json` per collection with something of theirs (`events.json`, `reflections.json` at every
  visibility, `drafts.json` with share links, `comments.json`, `notifications.json`, …), `accounts.json`
  (their account and linked family accounts, never a hash; a family account lists only this child),
  `mentions.json`, `files/<id>.<ext>` for every `/api/files/…` their data references, and `manifest.json`
  (with each file's original name).
- **Erasure**: `POST /api/admin/students/:id/erase { confirm: <their name> }` (admin; the name compared
  case- and space-insensitively) → `{ removed: { collection: n }, files, accounts, familyUnlinked }`. It runs
  `api.eraseStudent` on the server and `changed({ fn: 'eraseStudent', by, erased: { studentId, accounts } })`,
  deletes their uploaded files (and `.json` beside each) unless the record still references one, removes
  their account(s), unlinks them from family accounts (removing a family account that had only this child).
  Their share links stop working because their presentations are gone (404). `eraseStudent` is in
  `ADMIN_ONLY` (server/auth.mjs) and left out of `/api/action`'s allowlist, so the files and accounts can
  never be left behind by a record-only erase.
- **Audit**: each copy and erasure appends `{"at","action":"copy"|"erase","by":<account id>,"studentId"}` to
  `DATA_DIR/audit.log`. No names or content.
- **Activity log**: each copy and erasure is also in the activity log (`pdpa-copy`, `pdpa-erase`; see "Activity log"
  below). The activity log is kept for safeguarding, so erasure does not remove a student's entries: it replaces their
  name label (and the names of their removed accounts) with "Erased student" and keeps the ids.
- **Screens** (pilot only): Accounts has "A student's data" (download, and "Remove this student…" with
  "Type the student's name to confirm" and the reminder that backups hold the data for 30 days);
  the student's Privacy page and the parent's Consent page download their own copy; the PDPA page points
  to both.
- **Backups**: an erased student stays in the nightly backups until they roll over (30 by default).

## Protected uploaded files (`server/files.mjs`, `server/routes/30-uploads.mjs`, pilot only)

In a pilot, `GET /api/files/:name` serves a file only to someone who may read a record that uses it. Anyone else,
signed in or not, gets the same `404 { error: 'Not found' }` as a file that does not exist (never 403, so a name is
not confirmed). Demo mode is unchanged: anyone with the address, cached for a year.

- **`canSeeFile(user, name, meta)`** (`meta`: the `.json` beside the upload) is true for: the uploader (`meta.by`, the
  account id), so a file attached to nothing yet is theirs alone; anyone, signed in or not, when an open share link
  shows it (in `publicSnapshot(token)` of a link that is not revoked or expired: publishable moments, never hidden
  ones, and the presentation's own images); admin and leadership for feedback screenshots; anyone whose own copy of the
  record uses it (in `scopedSnapshot(user)`). That last rule gives the student their own files and, by `server/scope.mjs`,
  staff with reach at the levels they may read (never private moments), the class's teachers for class answers, a
  family only what the family view shows and not moments a moderator hid, and new store keys by the generic rule
  (an array of `{ studentId }` follows reach). An admin's **See as** (`GET /api/admin/preview/:id`) also opens that
  account's files for that admin for two hours (`previewing(admin, accountId)`).
- **Fast**: `fileIndex()` maps file name → the students whose records use it (`'*'`: a record tied to no one),
  built once after each change (keyed by the store's `rev` and the date). A file not in it goes to its uploader only; a
  person with none of those students in reach is refused without building their copy. Each person's set of files
  (from their scoped copy) and the share links' set are kept until the next change.
- **Headers**: `Cache-Control: private, no-cache` and `Vary: Cookie`, so each view (a cheap 304 with the ETag) is
  checked again and a file stops opening as soon as the record changes. Range requests are checked the same way.
  `GET /api/files/*` stays outside the sign-in guard (no 401), so a share page's photos load signed out.
- Tests: `server/test/protected-files.test.mjs` (every role, hidden moments, share links, class answers, See as, the

## Offline capture (`src/outbox.js`, `src/sync.js`, `src/components/OfflineBar.jsx`)

A signed-in pilot account can add moments (photos too) with no connection; they go when it is back. Server unchanged.
- **The queue on the device**: every change (`POST /api/action`) and every photo chosen offline is kept in IndexedDB
  (`tp-outbox`, store `items`, `{ k, uid, url, body }` or `{ k, uid, upload: { key, name, type }, blob }`), keyed by the
  signed-in account id and sent in order (`k`); a row is deleted once the server answers. No IndexedDB (a private
  window, blocked storage): the same queue in memory for that page. Demo mode (no account) keeps the old in-memory queue.
- **Photos offline**: `uploadFile` (`src/upload.js`), when the upload cannot reach the server and the app is live on
  it, hands the (shrunk) file to `holdUpload()`, which returns a placeholder `blob:<object url>#tpq-<key>` shown at
  once. Coming back, the photo is uploaded first (`POST /api/upload`) and every waiting change naming it is rewritten
  to `api/files/<id>.<ext>` before it is sent (`swapUrls`; an upload the server refuses becomes `""` and goes through
  `RefusedBar`). After a reload the placeholders are made again from the kept blobs, in this device's copy too.
- **Opening the app offline**: `loadAuth()` remembers a pilot sign-in (`localStorage['tp-offline-auth']`); with no
  connection at all (a network error, not a page without a server) it uses that, and `startSync({ user, offline })`
  runs on this device's copy of the record (`tp-store-*`) with the queue. The service worker keeps the page itself
  (`index.html`, cached as `?shell`) once a signed-in page posts `'shell'` (`keepShell()` in `src/pwa.js`), and serves
  it for a page load with no network before `offline.html`. It still never caches `/api/*`. Signing out deletes it with
  every other cache, so a signed-out phone shows the offline page as before; demo mode never asks for it.
- **Starting with changes left**: `startSync` takes up this account's rows only, keeps this device's copy (it already
  shows them), sends them, then fetches the server's copy.
- **Never under another account**: after being cut off (and on an offline start) `GET /api/auth/me` is asked before the
  next queued change; a different account (signed in in another tab) or nobody: that account's changes are not sent,
  dropped from the page's queue and kept on the device under their own account (sent when they sign in here again),
  and `RefusedBar` says "This browser is now signed in as …". A change the server refuses after reconnecting goes
  through `RefusedBar` as before.
- **Status**: the header (`SyncStatus`) shows "3 changes waiting" (Simple level: "Saved on this phone"), with the
  long words as its title; `OfflineBar` at the foot of the screen: "3 changes waiting. Saved on this phone. They will
  send when you are back online." (Simple: "Saved on this phone. It will send when you are back online."; Thai too),
  then "Sending … saved on this phone…" until it is done. Photos do not count as changes of their own.
- **Signing out** (`signOut`): with changes not sent, it asks first ("2 changes are not sent yet. Sign out anyway?");
  No keeps everything, Yes drops that account's rows only (other accounts' stay).
- Tests: `src/outbox.test.mjs` (`npm test`: per-account rows, in-memory fallback, rewriting, the words); browser:
  `node scripts/checks/offline-capture.cjs` (real roster from `TP_ROSTER`; `context.setOffline`): Aaron Torres on a
  phone adds a moment with a photo offline, reloads offline, comes back; Mr David Coultas, in his own context, sees the
  moment and the photo; the sign-out warning; a second account on the same browser never sends Aaron's queue.

## Class list sync from the SIS (`server/sis.mjs`, `server/routes/67-sis.mjs`, `src/components/SisSync.jsx`, pilot only)

The class lists can come from the school information system every night instead of an uploaded file. Nothing is applied
by itself: each check makes a change report that waits on Accounts until an admin applies or dismisses it. Settings, the
feed and the mapping file: `docs/roster-format.md`, "SIS sync".

- **Settings** (environment only, never in a data file): `SIS_URL` (the feed), `SIS_TOKEN` (sent as
  `Authorization: Bearer`), `SIS_SYNC_AT` (default `02:00`, `TP_TZ` time, Bangkok by default; `off` for no nightly check),
  `SIS_MAP` (a field-mapping file, relative to `DATA_DIR`), `SIS_TIMEOUT_MS` (default 60000). Without `SIS_URL` the panel
  says "Not set up" and files are imported as before. Demo mode: every route is 403 and nothing runs.
- **A check** (`check(req)` in `server/sis.mjs`; one at a time): fetch → a `transit-roster/1` file as is, anything else
  through `SIS_MAP` (`mapFeed`) → `api.parseRoster` → `buildReport`, compared with the record. Report statuses: `ready`
  (waiting for an admin), `nothing` (no changes), `invalid` (validation errors: the parser's `errors` and `missing`),
  `refused` (more than 10% of the record's students are gone from the feed: never staged, and the warning says to import
  a file by hand if it is right), then `applied`, `dismissed`, or `replaced` (a newer check came first). A failed fetch
  (unreachable, timeout, HTTP 401/403 "refused the token", not JSON, no map) makes no report: it sets `lastError`.
- **Report**: `{ id, at, by: { id, name } | null (nightly), mapped, status, school, counts, added / changed / leaving:
  { students, teachers, classes: { n, items (up to 200) } }, enrolments: { joins, ends, updated }, handover (as
  handoverPreview), accounts: { toCreate, leavers }, drop: { students, of, pct }, warnings, errors, base }`. `changed`
  items list `{ field, from, to }` (students: name, year, homeroom, advisor, programme, email, house; staff: name, email,
  roles, department; classes: name, subject, year, level, teachers). `leaving` leaves out records an applied report
  already had as gone (nobody is removed from the record, so they would otherwise come back every night).
- **Files**: `DATA_DIR/sis-sync.json` `{ status: { lastChecked, lastOk, lastError: { at, message }, lastScheduledDay },
  gone, reports (newest first, the last 10, each with `applied`/`dismissed` `{ at, by }`) }`; `DATA_DIR/sis-pending.json`
  `{ id, roster }`, the validated roster of the one `ready` report (removed on apply, dismiss or a newer check).
- **Routes** (admin only): `GET /api/admin/sis` → `{ configured, connected, lastChecked, lastError, syncAt, tz, mapped,
  checking, reports }` (never the URL or token); `POST /api/admin/sis/check` (Check now; 409 when not set up) → the same,
  plus `error`; `POST /api/admin/sis/reports/:id/apply { pauseLeavers? }` → the roster import's answer (summary, setup
  links for new accounts, paused, unpaused, accounts list) plus `sis`; 409 unless the report is `ready`, and when the
  record's class lists changed since the check (`base` ≠ `store.rosterImport.at`: someone imported a file); `POST
  /api/admin/sis/reports/:id/dismiss` → `{ sis }`.
- **Apply** runs `applyRoster(req, roster, opts)` (exported from `server/routes/15-roster.mjs`, which the file import now
  uses too): `api.importRoster` (so the year handover, ended class places and leavers' lists work as for a file), new
  accounts with setup links, unpaused returners, and the leavers' accounts paused when the admin ticks the box.
- **Nightly**: a timer every 30 s (and once a second after start) runs one check per local day when the time is between
  `SIS_SYNC_AT` and three hours later (`dueDay`), so a server restarted at 03:00 still checks that night and one started
  at noon waits for the next night.
- **Activity log**: `sis-fetch` (`detail.how` admin or schedule; the report status and counts, or `error` with status
  502; the nightly check has no actor), `sis-apply` (the import's counts and `detail.report`; paused and unpaused
  accounts get their own lines), `sis-dismiss` (`target.id` the report).
- **Screen**: Accounts › Class list sync: Connected / Not connected / Not checked yet, last checked, the nightly time,
  the last error; Check now; the waiting report (counts, then new, changed and leaving people and classes, class places
  joining and ending, advisor handovers, sign-in accounts to make, warnings) with "Apply these changes" and "Dismiss";
  after applying, "Download sign-in links (CSV)"; the last 10 checks with who applied or dismissed them.
- Tests: `server/test/sis-sync.test.mjs` (a mock SIS on localhost: good feed, mapped feed, bad token, 10% drop refused,
  invalid feed, stale report, dismiss, the last 10, the nightly run, applying a new year runs the handover, no token in
  any file or answer); browser: `node scripts/checks/sis-sync.cjs` (a mock SIS serving the real roster from `TP_ROSTER`,
  then a modified copy in memory; screenshots `tp-sis-*.png`).

## Advisor year sign-off (`src/api.js`, `src/components/YearSignoff.jsx`, pilot screens)

Near the end of the school year each advisor checks every advisee's year against a short checklist and signs it off;
leadership sees how far along each Year is. No new route: everything goes through `/api/action`, and the CSV is made in
the browser from the leadership copy of the record.

- **School year**: `schoolYearOf(date)` (August to July, `'2026-27'`), `schoolYearStart()` (1 August). Every record and the
  closing date belong to one school year; a new year starts with no sign-offs and no lock.
- **Checklist** (`signoffChecklist(sid)` → `{ student, year, items, met, total, record }`), worked out from the record as an
  advisor reads it (`getStudentMap(sid, 'advisor')`: private moments never count), each item with `label`, `what` (what
  counts), `met`, `detail` and `eventId` (the moment it links to, or null for the map): moments on at least N lines since
  1 August; at least one endorsed moment; a term reflection done (a finished `termReflections` row this year, or a reflection
  station); a goal set (open, dated this year or later) or met (`wasGoal`); Years 9 and 11, a **moving-up summary**, shown only
  when the record has `store.movingUp` (or `movingUpSummaries`/`movingUps`): an array of `{ studentId, status | doneAt … }` or
  an object keyed by studentId; done when `status` is done/ready/shared/finished/sent/final or a `doneAt`, `finishedAt`,
  `sharedAt` or `readyAt` is set (`movingUpOf(sid)`, a loose hook for that feature); Years 12–13, **CAS on track**: all three
  strands and at least `casHours` confirmed hours (default 50, Year 13 100; `signoffCasHours`); then the manual items the
  advisor ticks (default "Talked through the year together").
- **Settings**: `store.signoffSettings = { years: { [British Year]: { lines, endorsed, reflection, goal, movingUp, cas,
  casHours, manual: [{ id, label }] (≤ 5) } }, closes: { year, on, by, at } | null }`; `signoffSettingsFor(year)` fills the
  defaults (`SIGNOFF_DEFAULT`). `setSignoffYear(year, settings | null, by)` (null: back to the usual), `setSignoffClose(date |
  null, by)` (a day in this school year). After `closes.on` the year is locked (`signoffLocked()`): no ticks, sign-offs,
  "Not this year" or undo (409).
- **Records**: `store.yearSignoffs = [{ id: 'ys-…', studentId, year, advisorId, status: 'open' | 'signed' | 'notyet', ticks:
  { [manualId]: true }, reason, celebrated, at, by }]`, one per student per school year. Mutators: `tickSignoff(sid, itemId, on,
  by)`, `signOffYear(sid, by, { note? })`, `markNotThisYear(sid, by, reason)` (the reason is private to the advisor, ≤ 500),
  `undoSignoff(sid, by)` (back to open, until the year closes). Signing off stores `celebrated` (`{ lines, endorsed,
  reflection, goalsMet, goalsSet, movingUp, casHours }`, only what went well, never a gap) and tells the student in the app
  ("Ms Altemen signed off your year. Well done!", kind `milestone`, Thai in `NOTE_TH`). The **note for next year's advisor**
  is the advisor's handover note (`setHandoverNote`, see "Year handover"): the sign-off form shows it and changes it only when
  the text changed, so "Last year" and "Write handover notes" show the same note. Reads: `getSignoff(sid)`, `mySignoff(sid)`,
  `signoffProgress()` (per Year and homeroom: students, signed, notyet), `signoffCsv()`.
- **canAct** (`signoffOk` in `server/auth.mjs`): ticking, signing off, "Not this year" and undo only by the student's current
  advisor, as themselves (never leadership, admins, another advisor, the student or a family). Settings and the closing
  date: leadership as themselves, admins (as themselves, or null). **Activity log**: every change names the student and the
  advisor (`TOUCHES`); no note or reason is logged.
- **Scope** (`signoffScope` in `server/scope.mjs`): the current advisor gets their advisees' records whole and, for Years
  12–13, `store.signoffCas = { [sid]: confirmed hours }` (the hours entries themselves stay with CAS coordinators); leadership
  and admins every record as `{ id, studentId, year, status, at }` (counts, no ticks, notes or reasons); the student only their
  own once signed, as `{ id, studentId, year, advisorId, status, at, celebrated }` ("Not this year" is never sent to them);
  families and other staff nothing. `signoffSettings` goes to staff only. PDPA: the records carry `studentId` (copy and erasure).
- **Screens**: My advisory (pilot): "Year sign-off" with "Signed off: n of 23"; "Open year sign-off" lists each advisee with
  "k of N checks" and a status; "Check" shows the items (what counts, what the record has, "Open it" or "Open the map"), the
  ticks, the note for next year's advisor, "Sign off" (allowed with gaps, which it counts) or "Not this year" with a private
  reason; then "Undo sign-off" until the year closes. School overview (leadership and admins): "Year sign-off" by Year with a
  bar, each Year opening its homerooms, "Download as CSV" and "Checklist and closing date" (the date, and each Year's checklist).
  Student home (every level, after the conference card): "Your advisor has signed off your year", "<advisor> looked back at
  your year. What stood out:" and the celebrated lines, with "Hide" (remembered on that device). Thai: its own block at the
  end of `src/i18n.js`. Families get nothing new.
- Tests: `server/test/year-signoff.test.mjs`; browser: `node scripts/checks/year-signoff.cjs` (real roster: Ms Jane Altemen
  checks and signs off Aaron Torres for 8C with a note; leadership sees 8C 1 of 23, downloads the CSV, sets the closing date;

  activity log; axe). `thai-students.cjs` sweeps the card and the notification.
- Not done: no reminder to advisors who have not signed off; a closed year cannot be reopened for one student.
